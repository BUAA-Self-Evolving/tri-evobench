# Minimal L2 Stream Runtime

This package turns the materialized L2 pilot into an executable Flow. It provides:

- a generic ordered Stream runner;
- an OpenAI-compatible Chat Completions client;
- up to three Agent/User-Simulator Interactions per Episode;
- native-style binary SRA BigCodeBench evaluation after every Interaction;
- a learner call after every Episode;
- one persistent `workspace/.l2_state/` for the whole Stream.

The runtime keeps benchmark-private verifier records outside the shared Workspace under `benchmark_private/`. The API key is read only from `L2_API_KEY`; it is never accepted as a CLI argument or written to run artifacts.

## User input and prompts

The runtime currently has four distinct inputs; they should not be conflated:

1. The first user request of each Episode is static benchmark data from `episode.json.agent_view.request`. It is not generated by a model or fetched from an API.
2. `_AGENT_SYSTEM` in `runner.py` is the Task Agent system prompt. The Agent itself is invoked through the configured model API.
3. `BoundedRetryUserSimulator` in `user_simulator.py` creates the second or third user request after `fail` or `timeout`. It is a deterministic template and does not call an LLM.
4. `_LEARNER_SYSTEM` in `runner.py` prompts the configured model API after an Episode to summarize reusable memory for later Episodes.

The archived L1 demo provides useful prompt patterns—task request, Workspace summary, prior feedback, and JSON-only judge output—but it does not contain an independent LLM-driven User Simulator. Its runner directly appends evaluator feedback to the next Agent prompt or uses canned responses.

The pilot intentionally keeps that mechanism minimal: the initial request is read from benchmark data, and a deterministic bounded feedback message is appended only after a failed Interaction. It does not add an LLM User Simulator merely to imitate a production architecture. All attempts are retained, but `latest_interaction` is the declared terminal Episode result and the source used by the learner update.

## Setup, tests, and execution

Use the package-level `python demo.py list|check|test|run|smoke|package`
interface documented in `../README.md`. That file is the single source of
truth for commands; this runtime README only describes implementation details.
`pyproject.toml` is the dependency source of truth; the root
`requirements.txt` is only a pip-compatible editable reference to it.

The verifier tests execute both materialized reference solutions and deliberately broken mutations. They therefore validate positive and negative scoring paths, not just schema loading.

Run artifacts are written under `runs/<stream-id>/<run-id>/`:

- `workspace/.l2_state/memory.md`: learner state inherited by later Episodes;
- `workspace/.l2_state/episodes/`: normalized JSON envelopes for every Agent response and learner update;
- `benchmark_private/episodes/`: scores and verifier diagnostics;
- `report.json`: Stream-level outcome and artifact pointers.

## Security boundary

`--allow-unsafe-code-execution` is deliberately required. Generated Python runs in a temporary subprocess with a minimal credential-free environment, timeout, and Unix resource limits, but this is **not a security sandbox**. Use only on a trusted/disposable machine for this authorized demo. A production benchmark must replace this adapter with a container or stronger isolation boundary.

Each model artifact uses `model-response-0.1` and records its purpose, Stream/Episode/Interaction identity, model and provider IDs, finish reason, usage, response content, SHA-256 digest, and timestamp. It is a provider-neutral normalized record rather than a lossy `.txt` file or an unstable dump of one SDK's internal object. `memory.md` remains Markdown because it is projected learner state consumed by the next Episode, not a raw model-response artifact.
